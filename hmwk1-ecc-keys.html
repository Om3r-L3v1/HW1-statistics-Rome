Private key → public key

In Ethereum a private key k becomes a public key Q = kG through elliptic-curve scalar multiplication on secp256k1. Part 1 does the same thing on a small toy curve where every point can be drawn: choose k and the page adds the base point G to itself until it reaches kG, showing each addition. Part 2 repeats this for many keys and checks whether the outputs look random.

            DiscussionWhat the statistics can and cannot say
            
    
            
      
            
        
            Statistics can show that an output is clearly not random. They cannot show that a function is one-way. One-wayness is about how expensive it is to go backwards, and on these toy curves every key can be found by trying all n − 1 of them in a few milliseconds, however random the outputs look.
            

        
            Properties that matter for a one-way function
            
        
            Easy forward, hard backward. Double-and-add computes kG in roughly log₂ k steps. Going back is the elliptic-curve discrete logarithm problem, and its difficulty depends on the size of the group. For secp256k1 n ≈ 2256, so the best known attacks need about 2128 steps. None of the tests above measures this.
            
        
            One key, one point. The map k ↦ kG sends {1, …, n − 1} to the points other than O without repeats (in Test D no two keys give the same point). If k is chosen uniformly at random, Q is a uniformly random point of the group, which is what key generation needs. On the assignment curve mod 17 the group has 18 points and G = (1, 5) only reaches 9 of them.
            
        
            Structure is allowed. (a + b)G = aG + bG always holds (Test D), and digital signatures and key exchange (ECDSA, Diffie–Hellman) depend on it. The mirror symmetry kG ↔ −kG and the repeated x-values in Test B come from the same structure.
            

        
            Properties that belong to hash functions
            
        
            A hash should behave like a random function: every output value about equally likely, every bit equal to 1 half of the time, each flipped input bit changing each output bit with probability ½ (avalanche), and no usable relation between H(a), H(b) and H(a + b).
            
        
            The toy curve fails the last point completely. Anyone who knows Q = kG can compute (k + 1)G = Q + G or 2kG without knowing k, and x(kG) = x((n − k)G) for every k. The counts in Test B are also too regular: every x that appears, appears exactly twice. On the summary numbers (correlation, χ², bit balance, average avalanche) the curve and SHA-256 look about the same. These tests are needed for a hash, but they only see bit-level patterns and miss algebraic ones.
            
        
            The bias in the top bit is not caused by the curve. Both functions output a number below p, and p is not a power of two. For secp256k1, p is so close to 2256 that this bias is about 2−224.
            

        
            Why Ethereum uses both
            
        
            Ethereum needs the algebra of the curve for keys and signatures, and the random-looking output of a hash for addresses. The public key Q = kG is hashed with Keccak-256 and the last 20 bytes become the address, so the structure measured on this page does not carry over to the address.
