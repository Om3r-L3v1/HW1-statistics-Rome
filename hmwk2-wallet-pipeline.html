§2Kinds of operation

These are the letters on the steps above. The category is about what a step is for, not which algorithm it uses: SHA-256 and Keccak-256 both show up in more than one role.

Key generation vs key derivation. Randomness enters only once, at step 00. Everything after that is a deterministic function. Generation makes a secret; derivation turns one secret into many. If the entropy is weak, no later step can fix it. If it is strong, all the derived keys are as unpredictable as the entropy.

Hashing vs checksum vs encoding. A hash is a security primitive and has strong requirements. A checksum only has to catch accidents, so it can be short (4 bits in BIP-39, around 15 bits in EIP-55), and it can be made from a hash by keeping a few of its bits. An encoding only changes the representation: the BIP-39 words and the hex digits carry exactly the same bits as the bytes they stand for.

§3The standards

BIP-39 2013

Turns random entropy into a list of words that a person can write down, and turns those words into a binary seed.

In → out
128–256 bits of entropy → 12–24 words → 512-bit seed
Uses
A 2048-word list (11 bits per word), a SHA-256 checksum (ENT/32 bits), PBKDF2-HMAC-SHA512 with 2048 iterations
Kind
Encoding and checksum, then key derivation

BIP-32 2012

Hierarchical deterministic (HD) wallets: a whole tree of keys comes from one seed, so one backup covers every account.

In → out
Seed → master key + chain code → child keys at any path
Uses
HMAC-SHA512 and addition mod n on secp256k1
Detail
Hardened indices (≥ 2³¹, written ') need the private key. Normal indices only need the public key, so an extended public key (xpub) can produce child public keys for a watch-only wallet

BIP-44 2014

Fixes the layout of the BIP-32 tree, so that different wallets find the same accounts.

Path
m / purpose' / coin_type' / account' / change / address_index
Ethereum
m/44'/60'/0'/0/i, where 60 is Ether's number in the SLIP-44 coin list
Kind
A convention for key derivation (no new cryptography)

secp256k1 curve

The elliptic curve y² = x³ + 7 over the prime p = 2²⁵⁶ − 2³² − 977. It gives every private key a public key and makes signatures possible.

In → out
Private key k (1 ≤ k < n) → public key Q = k·G
Used for
ECDSA signatures on transactions; the sender's public key is recovered from the signature
Kind
Public-key cryptography (one-way because of the ECDLP)

Keccak-256 hash

The hash function Ethereum uses. It compresses the 64-byte public key into a 32-byte digest, and the address is the last 20 bytes.

Design
Sponge construction on the 1600-bit Keccak-f permutation, rate 1088 bits, capacity 512 bits
Note
Not the same function as the standard SHA3-256 (see §5)

EIP-55 2016

Puts a checksum into the letter case of the hex address. Software that ignores case still reads the same address.

In → out
Lowercase address → mixed-case address
Uses
Keccak-256 of the lowercase hex text; hash digit ≥ 8 means upper case
Strength
About 15 check bits on average, so a random typo gets through with probability ≈ 0.0247% (§4)

    What should be uniform and what should not

    Entropy and words have to be uniform. Twelve words only carry 128 bits if every word was chosen by a random generator; words picked by a person carry much less. The encoding is a bijection, so it neither adds nor removes entropy: 132 bits are written down, 128 random and 4 checksum.

    Seed, chain codes and private keys come from HMAC-SHA512 and PBKDF2, which behave like random functions. Private keys must be uniform in [1, n − 1]. If a value ever fell outside that range, BIP-32 would skip the index, but the probability is below 2⁻¹²⁷.

    The public key is not uniform. It is a point on the curve: only about half of all x values occur, y is fixed by x up to its sign (hence the 33-byte compressed form), and the map k ↦ Q has the algebraic structure we looked at in HMWK 1.

    The address no longer shows that structure after Keccak-256. Hex digits, bits and the avalanche test all look like a random 160-bit string. Finding two equal addresses would take about 2⁸⁰ tries (birthday bound).

    Checksums are only as good as the hash they come from. Because the check bits look random, an error passes with a probability we can predict: 1 in 16 for a 12-word phrase and about 1 in 4,000 for an EIP-55 address.

    Two generations of hash functions, and both are used in the wallet pipeline.

    Keccak-256 and SHA3-256 share the permutation, the rate and the capacity. The only difference is the padding. FIPS 202 adds two domain-separation bits before the padding, so the two functions give unrelated digests for the same input, even for the empty string (Keccak-256: c5d24601…, SHA3-256: a7ffc6f8…). Ethereum picked Keccak before SHA-3 was finalised and kept the original padding. That is why libraries offer both, and why "sha3" in Ethereum tools (the old Solidity sha3, now keccak256) means Keccak-256.

    §6Timeline

    The dates from the assignment, in order.

    1977
    RSARivest, Shamir and Adleman publish the first practical public-key scheme for encryption and signatures, based on factoring.
    2001
    SHA-2 · SHA-256, SHA-512Standardised by NIST as the successor of SHA-1.
    2012
    BIP-32 · HD walletsOne seed, a tree of keys.
    2013
    BIP-39 · mnemonic codeThe seed becomes 12–24 words that a person can write down.
    2014
    BIP-44 · multi-account hierarchyA fixed path layout, so wallets agree on where each coin and account is.
    2015
    SHA-3 standardised (FIPS 202)Based on Keccak, with a new padding rule. Ethereum had already chosen the original Keccak-256.
    2016
    EIP-55 · checksummed addressesMixed-case hex catches typos in addresses without changing the address format.

    The order matches the structure of the pipeline. Public-key cryptography and the SHA-2 hashes are decades older than the wallet standards. The key-management layer (BIP-32, BIP-39, BIP-44) was written for Bitcoin between 2012 and 2014, and Ethereum reused it with its own coin number. Ethereum's own pieces, Keccak-256 and EIP-55, are at the end of the chain and also came last: Keccak was chosen before SHA-3 was final, and the checksum was added when addresses were already in use.

    §7Why not one algorithm for everything?

    Each step has a different job, and the requirements of one job rule out the tools used for the others.

    JobStandardWhat the job needsWhy another tool doesn't fit
    Key management and derivationBIP-39 / BIP-32 / BIP-44A backup people can copy by hand, with error detection, turned into a seed by a slow function; then many keys from that one seed, along an agreed pathRaw hex is easy to copy wrongly. Independent random keys would each need their own backup. A signature scheme or a plain hash does neither job
    Public/private key relationship and signaturessecp256k1 (ECDSA)A public value that anyone can use to check signatures that only the private-key holder can produceA hash has no private/public pair, so it cannot sign. A checksum or an encoding has no secret at all
    HashingKeccak-256A short, fixed-length identifier that looks random and hides the structure of the public keyThe public key is 64 structured bytes. Hashing shortens it to 20 bytes, and the key itself stays hidden until the first signed transaction
    Checksum / error detectionEIP-55Error detection that changes neither the length nor the meaning of existing addressesAdding check digits would change the address format, and a hash alone doesn't tell the user that something was mistyped

    Keeping the jobs separate also means each part can be checked and replaced on its own: the word list, the derivation tree, the curve, the hash and the checksum. Ethereum did exactly this. It took Bitcoin's key management as it was and added its own hash and address format.

    §8Checking it in a real wallet

    MetaMask, Rabby, Rainbow, Exodus and most other wallets follow the same standards. With a throwaway wallet each step can be seen.

    1. Create a throwaway wallet. Use a separate browser profile, create a new wallet and write down the 12 words. That screen is BIP-39 key generation and encoding. Don't send real funds to it.
    2. Paste the phrase here. Account 0 above should be exactly the wallet's first account. This shows that BIP-39 → BIP-32 → BIP-44 → secp256k1 → Keccak-256 is deterministic.
    3. Add accounts. In MetaMask, "Add account" creates i = 1, 2, …; compare with the table of five accounts. Some wallets (Ledger Live, for example) change the account level instead (m/44'/60'/i'/0/0), so later accounts can differ between apps even though account 0 is the same.
    4. Export a private key. Account details → show private key. It is the value at step 05. Importing only that key gives a single account and no tree, because the chain code is missing.
    5. Look at the letter case. Copy your address, change the case of one letter and paste it into the checker above or into a send field. The wrong case is detected: that is EIP-55.
    6. Restore in a second wallet. Import the same phrase into Rabby or Rainbow and you get the same addresses. If a wallet supports a BIP-39 passphrase (most hardware wallets do), add one and every address changes.
