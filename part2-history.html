From Wallet Seed to Ethereum Address: History, Hash Families and Why One Algorithm Is Not Enough

This part covers when each piece of the Ethereum wallet pipeline appeared and how SHA-2 differs from Keccak/SHA-3. It also explains why a wallet chains several different primitives together instead of using one algorithm for everything.

1. Temporal and historical context

The Ethereum wallet pipeline was not designed as a single unit. It was put together over about four decades from parts built by different communities. Academic cryptography supplied public-key encryption and elliptic curves, NIST standardised the hash functions, the Bitcoin community wrote the wallet standards (BIPs), and Ethereum added its own address checksum (EIPs). The highlighted entries are the milestones asked for in the assignment. The grey entries give context.

    Diffie–HellmanPK
    Introduces the idea of public-key cryptography: two parties can agree on a secret over an open channel.
  2. 1977
    RSAPK
    Rivest, Shamir and Adleman publish the first practical public-key encryption and signature scheme, based on the difficulty of factoring large integers. Ethereum does not use RSA, but RSA established the private-key/public-key model the whole pipeline relies on.
  3. 1985
    Elliptic-curve cryptographyPK
    Koblitz and Miller independently propose public-key cryptography over elliptic curves. A 256-bit ECC key gives roughly the same security as a 3072-bit RSA key.
  4. 2000
    secp256k1 (SEC 2)PK
    The curve y² = x³ + 7 over a 256-bit prime field is published by the Standards for Efficient Cryptography Group. It was rarely used until Bitcoin adopted it.
  5. 2001
    SHA-2 family (SHA-256, SHA-512)Hash
    The NSA designs it and NIST publishes it (draft 2001, FIPS 180-2 in 2002). SHA-512 is used inside the wallet stack as HMAC-SHA512 in BIP-32 and PBKDF2-HMAC-SHA512 in BIP-39.
  6. 2007
    NIST launches the SHA-3 competitionHash
    Attacks on MD5 and SHA-1 lead NIST to look for a backup hash with a structurally different design from SHA-2.
  7. 2008–09
    Keccak submitted · Bitcoin launched
    Bertoni, Daemen, Peeters and Van Assche submit Keccak (2008). Bitcoin goes live in January 2009 using secp256k1 and SHA-256, which makes the curve standard practice for cryptocurrencies.
  8. 2012
    BIP-32: hierarchical deterministic walletsDerivation
    Pieter Wuille specifies how a single seed produces a whole tree of keys using HMAC-SHA512. In October 2012 NIST also announces Keccak as the SHA-3 winner.
  9. 2013
    BIP-39: mnemonic codeGenerationEncoding
    Defines how random entropy becomes a list of words (with a SHA-256 checksum) and how those words are stretched into a 512-bit seed with PBKDF2-HMAC-SHA512 (2048 iterations).
  10. 2014
    BIP-44: multi-account HD walletsDerivation
    Fixes a standard path layout, m / purpose' / coin_type' / account' / change / address_index, so different wallets derive the same addresses. For Ethereum the usual path is m/44'/60'/0'/0/i. The Ethereum Yellow Paper also appears in 2014 and specifies Keccak-256 as its hash.
  11. Jul 2015
    Ethereum mainnet (Frontier)
    Ethereum launches using Keccak-256 as it was submitted to the competition. This was about a week before SHA-3 was finalised.
  12. Aug 2015
    SHA-3 standardised (FIPS 202)Hash
    NIST publishes SHA-3 based on Keccak, with an extra domain-separation suffix in the padding. This small change is why Ethereum's hash is not the same function as SHA3-256 (see §3).
  13. 2016
    EIP-55: mixed-case checksum addressesChecksum
    Vitalik Buterin and Alex Van de Sande add error detection to hex addresses without changing their length or format. The capitalisation of each letter is set by the Keccak-256 hash of the address.
What the order shows. Each layer builds on tools that already existed. RSA (1977) established the public/private key model. ECC and secp256k1 gave smaller, faster keys. SHA-2 (2001) was a mature hash that the BIPs (2012–2014) used for key derivation. Keccak won the SHA-3 competition (2012) while Ethereum was being designed, so Ethereum committed to it before the FIPS 202 text was final (2015). EIP-55 (2016) came last, as a fix for a usability problem: hex addresses had no protection against typos.

2. SHA-2 / SHA-512 vs Keccak / SHA-3

Both are cryptographic hash functions. Each maps input of any length to a fixed-length digest and aims for preimage resistance, second-preimage resistance and collision resistance. They are related historically: SHA-3 was commissioned as a backup for SHA-2, not as a replacement, so NIST deliberately chose a winner with a very different internal design. Then if a new attack breaks one family, it is unlikely to break the other.

An Ethereum wallet therefore uses both families. SHA-2 appears in the key-management standards inherited from Bitcoin (BIP-32/39/44), and Keccak appears in everything Ethereum-specific (address, checksum).

3. Keccak-256 is not SHA3-256

Keccak-256 and SHA3-256 use the same permutation (Keccak-f[1600]), the same rate (r = 1088 bits), the same capacity (c = 512 bits) and the same 256-bit output. The only difference is one padding convention. When NIST wrote FIPS 202 it added two domain-separation bits (01) before the pad10*1 padding, so SHA-3 outputs cannot collide with outputs of the related SHAKE functions. Ethereum had already fixed its hash as the original Keccak, which has no suffix.

Keccak-256message …0x0100…000x80
SHA3-256message …0x0600…000x80

Changing that one byte changes every output. The values below are real test vectors, computed for this page:

input ""     Keccak-256 = c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
input ""     SHA3-256   = a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

input "abc"  Keccak-256 = 4e03657aea45a94fc7d47ba826c8d667c0d1e6e33a64a036ec44f58fa12d6c45
input "abc"  SHA3-256   = 3a985da74fe225b2045c172d6bd390bd855f086e3e9d525b46bfe24511431532
Practical pitfall. Many tools say "sha3" but mean Keccak. Early Solidity had a sha3() function and the EVM opcode is named SHA3, yet both compute Keccak-256. Solidity later renamed the function to keccak256() for this reason. Python's hashlib.sha3_256, by contrast, is the NIST version. If you hash a public key with standard SHA3-256 you get a wrong Ethereum address. Nothing reports an error, and the result does not match any real account.

Security is not affected by this difference. Both functions have the same strength. They are simply two distinct, incompatible functions, and a system has to pick one and use it consistently.

4. Why several techniques instead of one algorithm?

Each step in the pipeline solves a different problem and needs a different security property. No single primitive provides all of them. A hash function cannot produce signatures. A signature scheme does not give you a human-readable backup. A strong cryptographic hash is more than you need for catching typos, and a checksum provides no secrecy.

BIP-39 / BIP-32 / BIP-44

"How do I back up and organise many keys?"

Purpose: key management. One secret that a person can write down (the mnemonic) deterministically recreates an unlimited, well-organised tree of keys.

Property needed: the derivation is deterministic and one-way. Child keys reveal nothing about parents (hardened derivation), and every wallet that follows the standard reaches the same keys.

secp256k1

"How do I prove ownership without revealing the secret?"

Purpose: the private/public key relationship and ECDSA digital signatures that authorise transactions.

Property needed: a trapdoor asymmetry. Computing K = k·G is easy, recovering k is infeasible (ECDLP, about 2128 work), and anyone holding K can verify a signature.

Keccak-256

"How do I get a short, fixed identifier for this key?"

Purpose: hashing. It compresses the 512-bit public key into a 160-bit address, and the public key stays unrevealed until the first signature.

Property needed: preimage and collision resistance, with output that looks uniformly random so addresses are spread evenly.

EIP-55

"Did I copy this address correctly?"

Purpose: checksum and error detection for people copying and pasting addresses. It is not a security mechanism.

Property needed: cheap detection of accidental errors that stays backward-compatible. All-lowercase addresses remain valid, and no characters are added.

Why the pipeline is split up this way

Different security goals. One-wayness, trapdoor asymmetry, collision resistance and error detection are different mathematical properties. A hash provides one-wayness but has no trapdoor, so it cannot sign. Elliptic-curve multiplication has a trapdoor but produces 512-bit points and is not designed to work as a uniform fingerprint.

The same primitive can play different roles. The role depends on how a primitive is used, not on its name. Keccak-256 is a security-critical hash when it turns a public key into an address. It is only a source of pseudo-random bits for EIP-55, where it picks which letters to capitalise. SHA-512 works as a pseudo-random function inside HMAC (BIP-32) and as a deliberately slow key stretcher inside PBKDF2 (BIP-39).

Modularity and compatibility. BIP-32/39/44 were written for Bitcoin and are chain-independent. Ethereum reuses them unchanged and only selects coin type 60. Because the layers are separate, the same 12 words can drive Bitcoin, Ethereum and other chains, which is why wallets such as MetaMask, Rabby, Exodus and Rainbow produce the same address from the same phrase. A layer can also be replaced (for example a different signature curve) without redesigning the backup format.

Each layer gets the right cost. PBKDF2 is deliberately slow to make guessing passwords and phrases expensive. Keccak and ECDSA have to be fast because every node verifies every transaction. The checksum has to cost almost nothing. A single algorithm cannot be slow and fast at once.

These figures show why each layer is safe enough for its own job, and why a checksum is deliberately much weaker than a hash.
